## ルールの裁定

草案（`お化け退治ボードゲーム草案.md`）の未定義箇所について、2026-11-13 にユーザーが裁定した。R-01〜R-13 は rules.md v0.1 に反映済みである。

- R-01：人間移動で行き先の辺に通せん棒がある場合は、外周の壁と同じ扱いにする（移動せず向きだけ変える）。→ §5.1
- R-02：プレイヤー駒は他のプレイヤー駒のいる部屋に入れる。→ §5.2
- R-03：お化けには向きがない。お化け移動で外周の壁に当たる場合は何も起きない。草案の「向きだけを変更する」は誤記として扱う。→ §5.4
- R-04：「空間を分断する配置」とは、設置後に通せん棒のない辺だけで 36 部屋すべてが連結しなくなる配置をいう。→ §5.5
- R-05：怨霊との接触は、人間が怨霊の部屋に入った場合と、怨霊がプレイヤーのいる部屋に入った場合の両方で発生する。→ §7.2
- R-06：接触で失うチップは本人が選び、ゲームから取り除く。チップがなければ何も失わない。ゴールデンを失えば 3 点減る。→ §7.2
- R-07：スタート地点に戻った駒は開始時の向きに戻す。→ §7.2
- R-08：怨霊をスタート地点へ動かすカードは使用でき、怨霊は移動しない（壁と同じ扱い）。→ §7.3
- R-09：お化けの配置先に怨霊やプレイヤーがいてもそのまま置く。プレイヤーがいる部屋のチップは次の獲得判定でそのプレイヤーが取る。→ §8.3
- R-10：§7.5(b) の「お化けカードを 3 枚めくる」は、めくった後に配置の手順でお化けを置くことを含む。→ §7.5、§8
- R-11：10 点に達した場合、その獲得判定のその場で終了する。→ §6.5、§9.1
- R-12：お化けカードの山札が 0 枚になった時点でゲームを終了する。最後にめくった 3 枚のお化けは配置しない。→ §8.2、§9.2
- R-13：最終得点が同点の場合は引き分けとする。→ §9.2

### 設計書の作成時に補った箇所（要確認）

次の各項は、裁定 R-01〜R-13 から自然に導かれる扱いとして rules.md v0.1 に記載した。結果に影響しうるため、異論があれば rules.md の改訂として扱う。

- R-14：スタート地点の割り当て。2 人は対角（A1 と F6）、3 人は A1・F1・F6、4 人は時計回りに A1・F1・F6・A6 とする。→ §2.6
- R-15：移動カードの手札は持ち主以外に非公開とする。使用したカードと獲得チップは公開とする。→ §3.4、§4.3、§6.4
- R-16：1 回の獲得判定で複数人が 10 点以上に届きうる場合、判定順（手番プレイヤーから席順）で先に 10 点に達したプレイヤーが勝つ。→ §6.5
- R-17：複数人が同時に怨霊と接触した場合、手番プレイヤーから席順にペナルティを処理する。→ §7.2

## 実装の設計判断

- D-01：技術構成は TypeScript（strict）＋ React ＋ Vite ＋ Vitest とする。`vite-plugin-singlefile` で 1 枚の HTML にまとめ、GitHub Pages に公開する。オンライン同期は Supabase（テーブル 1 つ、Realtime、匿名ログイン）、受け入れ検査は Playwright、盤面の描画は SVG とする。
- D-02：ゲームロジックは「選択待ち」モデルを採る。カードの選択と対象の選択が分かれ、さらにペナルティのチップ選択や §7.5 の選択が効果の途中に入るためである。
- D-03：乱数は mulberry32 とし、32 ビットの内部状態を `GameState.rng` に持つ。`Math.random()` はゲームロジックで使わない。ロビーでのシードと部屋コードの生成に限り `crypto.getRandomValues` を使う。
- D-04：選択肢 ID と乱数の消費順は通信プロトコルの一部として実装設計書 §6 に固定する。変更する場合は理由をここと `CLAUDE.md` に残す。
- D-05：オンライン版の共有ドキュメントには山札と手札の並びが入る。開発者ツールで他人の手札を覗けるが、身内で遊ぶ前提のため、この制約を受け入れる。画面と DOM には他人の手札を出さない。
- D-06：Supabase では、`rooms` テーブルの更新を RPC 関数 `write_room` に限る。関数内で版の一致と書き込み者の着席を検査する。不正な手（ルール違反の手）の検査はサーバー側では行わず、各ブラウザの `replay` で弾く。
- D-07：設計文書の正は claude.ai プロジェクトとする。Claude Code の作業用に、rules.md・実装設計書・decisions.md の写しをリポジトリの `docs/` に置く。写しの同一性は rules.md と設計書の版番号で確認する（2026-11-14、decisions.md を写しの対象に追加）。
- D-08：GitHub Pages のビルド時に Supabase の URL と publishable key を環境変数で埋め込む。値が未設定の場合、オンライン対戦の入口を隠してローカル対戦だけを提供する。
- D-09：Supabase の鍵は publishable key（`sb_publishable_`）を使う。レガシーの anon key は Supabase が 2026 年末までに廃止する方針のため使わない。publishable key はブラウザに公開してよい低権限の鍵であり、守りは RLS と `write_room` 関数が担う。secret key はどこにも置かない（2026-11-13、設計書 v0.2）。
- D-10：GitHub と Supabase の準備手順は setup.md に分ける。Node.js は 24 系（Active LTS）に固定する。
- D-11：第 2 段階と第 3 段階の分担を見直した。人間移動による怨霊との接触（§7.2(a)）、ペナルティ、§7.5 の重なりの選択は第 2 段階で実装する。対象の選択が要るお化け移動カードと通せん棒カードの効果は第 3 段階にまとめる（2026-11-15、設計書 v0.3）。
- D-12：第 1 段階では React の型定義（`@types/react`・`@types/react-dom`）を入れていないため、`src/main.ts` は React を使わない仮の入口になっている。第 4 段階で React の画面を作るため、この 2 つの追加を 2026-11-15 にユーザーが承認した。
- D-13：性質テストの終局手数の上限を 5000 から 20000 に改めた。第 2 段階の実装（お化け移動・通せん棒は効果なし）で乱択プレイアウトを 300 シードずつ測ったところ、終局までの手番数の中央値は 2 人 1052・3 人 1158・4 人 1187、最大は 4152 であり、5000 では性質テストが偶然に失敗しうるためである（2026-11-15、設計書 v0.4）。
- D-14：`targets.ts` に `targetOf` の逆である `optionOfTarget` を公開する。`explain` が対象から選択肢 ID を引くために使い、UI でも対象から選択肢を作るときに使ってよい（第 3 段階で追加、2026-11-15）。
- D-15：`targetOf` は、局面に存在しない対象を指す選択肢（手札にないカード、盤上にないチップ、盤外の辺）に例外を投げる（第 3 段階、2026-11-15）。
- D-16：GitHub Pages への公開（`deploy.yml`）を第 5 段階から第 4 段階に前倒しする。ユーザーがスマートフォンでローカル対戦を通して遊び、第 4 段階の受け入れを確かめられるようにするためである。Supabase の値が未設定の間は D-08 によりオンライン対戦の入口が隠れるため、前倒ししても問題はない（2026-11-15、設計書 v0.5）。
- D-17：ローカル対戦の開始時のシードは `crypto.getRandomValues` で生成してよい（D-03 の例外に加える）。受け入れ検査のために、URL の `?seed=<数>` でシードを指定できるようにする。

## UX 上の暫定判断

いずれも暫定である。異論があれば変更する。ui_design.md はまだない。見た目は boardgame-flavor-art での策定を待ち、それまでは実装設計書 §8 の最低限の表示とする。

- U-01：操作はクリック（タップ）中心とする。手札のカードをタップして選ぶ。お化け移動カードと通せん棒カードは、選んだ後に盤面の対象（チップ・怨霊・辺）をタップする。
- U-02：人間移動カードを選ぶ前に、カードへのホバー（スマートフォンでは 1 回目のタップ）で移動先をプレビュー表示する。2 回目のタップで確定する。
- U-03：カードを選んで対象を選ぶ前であれば、「選び直す」で取り消せる（`undoLast` による）。
- U-04：画面は幅 375px のスマートフォン縦画面を基準に組む。
- U-05：ローカル対戦では、手番が替わるたびに目隠し画面を挟み、タップで次の人の手札を表示する。
- U-06：怨霊との接触で失うチップは、1 種類しか持っていない場合は選択を求めず自動で失う（両方持っている場合だけ選ぶ）。
- U-07：`explain` の文言は、設計書の例（手番外、連結条件）以外を Claude Code が決めた。手番プレイヤー以外のペナルティの選択を待っているときは「席 N の選択を待っています」と表示する（第 3 段階）。

## 観察事項（後続の作業への申し送り）

- O-01：手番数の上限がないため、誰もチップを取れない展開が続くと終局しない可能性がある。お化けカードは配置のときにしか減らない。実装では性質テストで乱択プレイアウトの終局手数を測り、長すぎる場合は boardgame-balance-sim で扱う。実装側でルールを変えて対処しない。
  - 2026-11-15 の測定（第 2 段階、乱択、各人数 300 シード）：900 局すべてが終局した。10 点での決着が 91〜98%、お化けカードの山札切れでの決着が 2〜9% である。乱択のプレイヤーは目的なく歩くため手番数（中央値 1000 強）は人の対局の目安にならない。実際の長さは、チップへ向かう方針のエージェントで boardgame-balance-sim が測る。
  - 2026-11-15 の測定（第 3 段階、全ルール、乱択、各人数 200 シード）：600 局すべてが終局した。手番数ではなく applyMove の回数で、中央値は 2 人 1277・3 人 1390・4 人 1238、最大は 4313 である。10 点決着は 2 人 200・3 人 198・4 人 197 局、山札切れ決着は 0・2・3 局である。
